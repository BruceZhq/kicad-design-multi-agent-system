# RatsNest 不足总结（用于后续改进）

> 记录日期：2026-07-15
> 来源：代码走读 + 讨论中提出的质疑
> 目的：沉淀问题清单，方便后续迭代改进

---

## 一、能力范围过窄（核心不足）

**现状**
- 只支持 2 种电路家族：TLV1117 可调 LDO、LM2596 异步 Buck
- 自动修复只覆盖 3 类问题，映射表仅 4 条：
  - `fill_mpn`（填料号）
  - `feedback_divider`（反馈分压电阻）
  - `led_resistor`（LED 限流电阻）
- 除这 3 类外的问题一律「升级给人工」，系统不处理
- `template` 后端更窄：只生成原理图，连 PCB 都不产出，遇到 Buck 直接报错

**问题**
- 定位更像「稳压小板专用工具」，不是通用电路设计系统
- 大量常见硬件问题完全不覆盖：电容选型、走线阻抗、EMC、散热、电源纹波、接地回路、元件极性等
- 文档自认「任意拓扑综合、法规认证、完整集群验证」都属「未来阶段」= 尚未实现

**改进方向（待定）**
- 扩充电路家族（明确下一个要支持哪种拓扑）
- 增加修复器种类与映射规则
- 让 `template` 也能产出 PCB，或明确其只作基准用途

---

## 二、公式的通用性存疑

**现状**
- 修复依赖少数几个写死的物理公式（分压公式、欧姆定律等）
- 这些公式只在「限定电路家族内」严格成立

**问题**
- 公式无法适应限定家族之外的情况（如开关电源补偿网络）
- 系统靠「把问题范围死死限制在公式成立处」来回避通用性问题——治标不治本
- 覆盖面扩大时，每种新拓扑都要人工新增求解器，扩展成本高

**改进方向（待定）**
- 评估是否引入更通用的电路求解/仿真能力（如 SPICE 联动，代码里已有 `spice.py`，待确认成熟度）
- 建立可扩展的求解器框架，降低新增拓扑的成本

---

## 三、大模型能力被限制过严

**现状（LLM 在系统中的角色被严格约束）**
- 不能写 KiCad 文件（只能提议）
- 不能决定电气值（由确定性求解器计算）
- 修复时只能「批准 / 否决 / 解释」，不能改值、不能发明新修法
- 不能新增工具权限（AHE 也不行）
- 连提示词都固化在策略包 YAML 里

**问题**
- LLM 实际沦为「审核员 + 翻译官」，几乎没有创造性发挥空间
- 「安全可控」与「智能上限」之间的取舍偏向了极端保守一侧
- 在探索性设计场景下，这种限制会明显拖累能力

**背景（这是有意取舍，非纯缺陷）**
- 硬件零容错：板子出错代价高（打样/量产/安全）
- 因此选择「窄而可靠」而非「宽而不可控」
- 换来的优点：可复现、可审计、修不好会回滚、不认识的问题交给人

**改进方向（待定）**
- 探讨在「非量产/探索阶段」放宽 LLM 约束的分级模式
- 保留量产路径的强约束，另开一条「实验探索」路径给 LLM 更大自由

---

## 四、整体定位判断

**当前更像：** 架构演示 / 方法论验证，而非可用产品
- 想证明的命题：如何在零容错的硬件领域安全引入 LLM
- 答案：把 LLM 关进「确定性 + 可进化知识库」的笼子里

**结论**
- 作为方法论验证：当前范围（2 种电路 + 3 类修复）够用
- 作为实用产品：能力广度差得远，真正值钱的「任意拓扑综合」尚未实现
- 需警惕漂亮架构话术掩盖实际能力的狭窄
